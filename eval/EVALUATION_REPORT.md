## 1. Evaluation Framework

### Dataset
- **65 valid semantic questions** across 6 question types and 3 difficulty levels
- Questions generated by LLM, covering 40+ arxiv papers in the corpus
- Each question has ground-truth `expected_paper_ids` for retrieval evaluation

### Question Distribution
| Difficulty | Count | Types |
|-----------|-------|-------|
| Easy | 22 | concept_locate (18), negative (4) |
| Medium | 26 | method_detail (14), fact_extract (10), negative (2) |
| Hard | 17 | comparison (8), trend_synthesis (5), negative (4) |

### Metrics
- **NDCG@5** (primary) — Normalized Discounted Cumulative Gain, measures ranking quality
- **MRR** — Mean Reciprocal Rank, measures how early the first relevant result appears
- **Precision@5** — Fraction of top-5 results that are relevant
- **Recall@5** — Fraction of relevant papers found in top-5
- **Latency p90** — 90th percentile retrieval latency

### Methodology
1. **Retrieval-only evaluation**: Directly call the retrieval pipeline (vector search + BM25 hybrid fusion) without LLM synthesis. This isolates retrieval quality from generation quality.
2. **Systematic ablation**: Sweep each parameter independently while holding others at defaults. Measure NDCG@5 across all 65 questions per configuration.
3. **Optimal combination test**: Apply best values from ablation studies simultaneously and verify interaction effects.

## 2. Ablation Study Results

### 2.1 retrieval_k — Number of Retrieved Chunks

| k | NDCG@5 | MRR | Recall@5 | Latency p90 |
|---|--------|-----|----------|-------------|
| 4 | 0.3259 | 0.3727 | 0.3199 | 0.82s |
| **8** (default) | 0.3325 | 0.3773 | 0.3258 | 0.93s |
| **12** | **0.3454** | **0.3803** | **0.3388** | 0.90s |
| 16 | 0.3454 | 0.3803 | 0.3388 | 0.80s |
| 20 | 0.3481 | 0.3803 | 0.3434 | 2.29s |

**Finding:** k=12 captures most of the improvement (+3.9% NDCG) without latency penalty. k=20 shows diminishing returns with 2.5x latency increase. The improvement comes entirely from hard questions (0.2042 → 0.2588), while easy and medium remain stable.

### 2.2 hybrid_alpha — Vector vs BM25 Weight

| alpha | NDCG@5 | Easy | Medium | Hard |
|-------|--------|------|--------|------|
| 0.0 (pure BM25) | 0.2088 | **0.0000** | 0.3596 | 0.2195 |
| **0.3** | **0.3374** | 0.3889 | 0.3596 | **0.2250** |
| 0.5 | 0.3369 | 0.3889 | 0.3596 | 0.2232 |
| **0.72** (default) | 0.3325 | 0.3889 | 0.3596 | 0.2042 |
| 0.85 | 0.3325 | 0.3889 | 0.3596 | 0.2042 |
| 1.0 (pure vector) | 0.3325 | 0.3889 | 0.3596 | 0.2042 |

**Finding:** alpha=0.3 is optimal. Key insight: Pure BM25 (alpha=0.0) catastrophically fails on semantic queries (easy NDCG = 0.0), confirming that vector search is essential for semantic understanding. However, increasing BM25 weight from 28% to 70% improves hard questions by 10%, as keyword matching helps locate specific papers in multi-paper queries.

### 2.3 final_context_k — Chunks Passed to LLM

| k | NDCG@5 | Impact |
|---|--------|--------|
| 2 | 0.3325 | None |
| 3 | 0.3325 | None |
| 5 | 0.3325 | None |
| 8 | 0.3325 | None |

**Finding:** This parameter has **zero impact on retrieval quality** (as expected — it only controls how many retrieved chunks are passed to the LLM for answer synthesis). Relevant only for generation quality evaluation.

### 2.4 hybrid_oversample — Vector Search Oversample Factor

| Factor | NDCG@5 | Latency p90 |
|--------|--------|-------------|
| 1.5 | 0.3325 | 0.90s |

## 4. System Characteristics

### Strengths
1. **Semantic concept matching** (39% NDCG) — vector search effectively handles paraphrased queries
2. **Technical detail retrieval** (43% NDCG) — method_detail is the strongest category
3. **Negative query rejection** (100% correct) — system correctly returns no relevant results for out-of-scope queries
4. **Low latency** (0.6s p90 optimized) — sub-second retrieval for most queries

### Weaknesses & Improvement Opportunities
1. **Multi-paper queries** (comparison: 15% NDCG) — single-query retrieval struggles to find both papers simultaneously
2. **Fact extraction** (26% NDCG) — precise factual queries need better chunk-level granularity
3. **~60% of questions miss** — the binary hit/miss pattern (NDCG either 1.0 or 0.0) suggests embedding quality is the bottleneck, not ranking

### Root Cause Analysis
The binary distribution of scores (most questions score either 1.0 or 0.0) indicates the primary bottleneck is **embedding representation quality**, not the retrieval/ranking algorithm. Papers that happen to be well-represented in the embedding space are found perfectly; others are completely missed regardless of parameter tuning. Potential improvements:
- Query expansion (decompose multi-paper queries into sub-queries)
- Chunk augmentation (add paper title/abstract to each chunk for better matching)
- Fine-tuned domain embeddings
